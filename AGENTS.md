# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## Project Configuration

- **Language**: TypeScript
- **Package Manager**: pnpm
- **Framework**: SvelteKit (Svelte 5, runes mode forced) + Tailwind CSS v4
- **Deploy target**: Cloudflare Workers via `@sveltejs/adapter-cloudflare`

## Commands

```bash
pnpm dev            # vite dev → http://localhost:5173 (needs http://localhost for camera)
pnpm build          # wrangler types --check && vite build
pnpm preview        # run the built worker locally on :4173
pnpm check          # wrangler types + svelte-kit sync + svelte-check (typecheck)
pnpm lint           # prettier --check . && eslint .
pnpm format         # prettier --write .
pnpm release        # build, then wrangler deploy → draw.thoran.art
pnpm gen            # regenerate worker-configuration.d.ts (wrangler types)
```

There is no test suite. Verify changes with `pnpm check` (types) and by running `pnpm dev` and using the camera. The camera requires a secure context, so `http://localhost` or HTTPS only.

## Architecture

Drawer is a **fully client-side** webcam hand-tracking drawing app. There is no
backend or persistence — the Cloudflare Worker only serves static assets. The
hand-landmark model and MediaPipe WASM runtime are fetched from CDNs at runtime
(`src/lib/tracking/tracker.ts`), so the camera feed never leaves the device.

The central design tension is **imperative per-frame tracking** vs. **reactive
Svelte UI**. These are deliberately kept separate:

- **`src/lib/tracking/tracker.ts`** — the imperative core. A `Tracker` class owns
  the camera stream, the MediaPipe `HandLandmarker`, three canvases, and the
  `requestAnimationFrame` loop. Everything that runs every frame lives here.
  - Three canvases: `view` (visible, composited output), `proc` (offscreen —
    holds the mirrored/selfie frame fed to the detector), and `strokes`
    (offscreen — the persistent paint layer that survives across frames).
  - Right hand draws (index-finger pointing gesture → EMA-smoothed line onto the
    stroke layer); left hand sets brush width via a thumb-index pinch and never
    paints. Both are tracked simultaneously.

- **`src/lib/state.svelte.ts`** — the *only* bridge from the loop to the DOM. A
  single `$state` object (`hud`) that the tracker mutates each frame (fps writes
  are throttled to avoid strobing). Svelte components read `hud.*` and re-render
  only the fixed HUD chrome. Do not add reactive per-frame data flow anywhere
  else — anything hand-anchored is painted on the canvas instead (see below).

- **Hybrid UI split** — hand-anchored chrome (skeleton, "draw" chip, width meter)
  is painted directly on the canvas in `src/lib/tracking/render.ts` because it
  must follow landmarks cheaply every frame. Only fixed chrome (start overlay,
  hint bar, clear button) lives in the DOM as Svelte components under
  `src/lib/components/`.

- **`src/lib/tracking/gestures.ts`** — pure gesture math (pointing detection,
  pinch amount, handedness classification, clamp/mapRange). `landmarks.ts` holds
  landmark indices, hand topology, and all brush/smoothing tuning constants.

### Palette: single source of truth

Colors are defined once in `src/routes/layout.css` under Tailwind's `@theme`,
which emits both `:root` CSS custom properties and utility classes. The DOM uses
the utilities; the canvas cannot, so `src/lib/tracking/palette.ts` reads the same
CSS variables at runtime (`resolvePalette()`, called on `Tracker.enable()`) into
a plain `palette` object. When changing colors, edit `layout.css` and keep the
`Palette` interface / token names in `palette.ts` in sync.

### SvelteKit specifics

- `src/routes/+page.ts` sets `ssr = false` (browser globals + MediaPipe must not
  run on the worker) and `prerender = true` (the shell is prerendered static
  HTML). Keep camera/MediaPipe code out of any server-run path.
- Runes mode is forced for all non-`node_modules` files (see `vite.config.ts`).
- `worker-configuration.d.ts` is generated by `wrangler types` — do not edit by
  hand; regenerate with `pnpm gen`.

Note: this project was ported from an earlier Python/vanilla-JS version. Some
comments still reference that origin (e.g. BGR color tuples).

You are able to use the Svelte MCP server, where you have access to comprehensive Svelte 5 and SvelteKit documentation. Here's how to use the available tools effectively:

## Available Svelte MCP Tools:

### 1. list-sections

Use this FIRST to discover all available documentation sections. Returns a structured list with titles, use_cases, and paths.
When asked about Svelte or SvelteKit topics, ALWAYS use this tool at the start of the chat to find relevant sections.

### 2. get-documentation

Retrieves full documentation content for specific sections. Accepts single or multiple sections.
After calling the list-sections tool, you MUST analyze the returned documentation sections (especially the use_cases field) and then use the get-documentation tool to fetch ALL documentation sections that are relevant for the user's task.

### 3. svelte-autofixer

Analyzes Svelte code and returns issues and suggestions.
You MUST use this tool whenever writing Svelte code before sending it to the user. Keep calling it until no issues or suggestions are returned.

### 4. playground-link

Generates a Svelte Playground link with the provided code.
After completing the code, ask the user if they want a playground link. Only call this tool after user confirmation and NEVER if code was written to files in their project.
